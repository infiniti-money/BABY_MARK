# BABY_MARK: Cloudflare runtime and storage audit

Verified against current official documentation on 24 November 2026. This note describes platform constraints and architecture recommendations. It does not claim that any implementation has been deployed or benchmarked, and no production resources were changed.

## Supported target and image trust

The requested deployed application can use static Pages assets, Pages Functions, D1 and ordinary Workers KV. Keep the existing Node/Sharp implementation out of the Functions dependency graph. Standard Sharp needs a Node-API compatible runtime; Cloudflare's official vinext project explicitly warns that Workers cannot load native Node-API addons such as Sharp. Sharp's optional Wasm build also requires multi-threading, while Workers do not support Wasm threads. A successful Node test of Sharp therefore does not establish Cloudflare compatibility. [Sharp installation](https://sharp.pixelplumbing.com/install/), [Cloudflare vinext compatibility](https://github.com/cloudflare/vinext), [Workers Wasm](https://developers.cloudflare.com/workers/runtime-apis/webassembly/)

Workers provide JavaScript, WebAssembly and listed web APIs; a browser Canvas implementation must not be assumed to exist in this server runtime. A custom single-thread Wasm codec/compositor is technically possible, but needs its own measured bundle, memory, CPU and Vietnamese text-rendering acceptance tests. Workers Free permits 10 ms CPU per HTTP request and 128 MB memory per isolate, including Wasm allocations. Repeated JPEG encoding to reach a hard byte cap must be benchmarked before being described as free-tier compatible. [Workers web APIs](https://developers.cloudflare.com/workers/runtime-apis/web-standards/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

Cloudflare Images now supports raw bytes, text rasterization, image overlays and JPEG output through an Images binding. This could enable server composition, but adds the Images product beyond the selected Pages/Functions+D1+KV architecture. Its free plan currently allows 5,000 unique transformations per month; the application must not silently add that binding or promise unlimited free server rendering. [Images binding](https://developers.cloudflare.com/images/optimization/binding/), [Images pricing](https://developers.cloudflare.com/images/pricing/)

The practical implementation within the selected resources is browser Canvas composition with 40% floating panels, then upload of a JPEG no larger than 200,000 bytes. JPEG has no alpha channel: the transparent overlay is blended into the camera photograph before JPEG encoding. The UI and records should explicitly call this a client-rendered attachment. The server can establish authenticated employee identity, server receipt time, assigned branch and shift, computed distance from supplied GPS, one-use challenge, byte length and SHA-256. These controls bind accepted bytes and metadata to a submission. They do not prove camera liveness, GPS authenticity, visual text correctness or that the uploaded photograph was captured at the claimed location. Even server composition would not prove those underlying physical facts.

## KV consistency, budget and expiration

KV is eventually consistent; writes and negative lookups can remain stale at other locations for 60 seconds or more. Never use it as the authority for revocation, attendance uniqueness, one-use tokens or the global byte budget. Use D1 constraints/conditional writes and immutable, unpredictable KV keys. Photo reads must check D1 access and retention state before returning bytes, with private/no-store responses. A newly accepted photo may temporarily be unavailable from another edge; the UI should offer a bounded retry instead of treating that delay as missing attendance. [How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/)

Free KV currently includes 1 GB stored data per account and namespace, 100,000 key reads/day, and 1,000 each of writes, deletes and list requests/day. Writes to the same key are limited to once per second. Daily quotas reset at 00:00 UTC, and operations of an exceeded type fail. A separate photo namespace helps accounting but does not expand the account-wide storage allowance. [KV limits](https://developers.cloudflare.com/kv/platform/limits/), [KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)

For 50 employees and two punches daily, 100 immutable photo writes/day leave reasonable quota headroom. At the maximum size, however, 50 × 2 × 60 × 200,000 = 1,200,000,000 bytes. A 900,000,000-byte rolling budget stores 4,500 maximum-size photographs, or approximately 45 full days. Sixty days is a maximum lifetime, not a guaranteed minimum. To retain all 60 days at that punch frequency, the average must be at most 150,000 bytes/photo. Extra shifts and retakes reduce the effective window further. These are capacity calculations, not measurements of actual usage.

Set KV expiration to the server acceptance timestamp plus 60 days, and deny reads after that timestamp independently. `expirationTtl` has a 60-second minimum. D1 should retain a photo inventory with byte size, lifecycle state and oldest-first ordering. Reserve capacity atomically in D1 before uploading; do not implement a read-sum-then-write race. D1 and KV do not share a transaction: failures need explicit states and retryable reconciliation. Budget accounting must not release physically stored bytes merely because deletion was requested; a failed KV deletion still consumes storage. Avoid unbounded eviction loops because each delete consumes quota and each invocation has operation limits. [KV writes and expiration](https://developers.cloudflare.com/kv/api/write-key-value-pairs/)

## D1, retention and scheduled work

D1 `batch()` executes prepared statements sequentially as a transaction; a failed statement aborts/rolls back the batch. Use it for related attendance, nonce, audit and reservation changes. Build invariants into unique/check constraints or conditional statements so concurrent requests cannot both pass a prior JavaScript read. KV writes cannot be included in this transaction. [D1 database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)

Free D1 permits 500 MB/database, 5 GB/account, 50 database queries per invocation and 100 bound parameters per query. Two years of 100 daily attendance events is about 73,000 rows; indexed metadata at that scale is plausible, but actual stored row and index sizes still require measurement. Images belong in KV, not D1. Use date/store/employee indexes, server-side filtering and pagination, bounded maintenance batches, and distinguish a 24-calendar-month policy from a fixed 730-day approximation. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)

Pages Functions expose request handlers; creating a route named `cron` does not schedule it. Cloudflare Cron Triggers invoke a Worker's `scheduled()` handler, and execute in UTC. Within a strict Pages/Functions-only runtime, use KV TTL for physical photo expiration and run bounded, authenticated D1 maintenance on traffic or operator request. This cannot guarantee deletion of expired D1 rows while the application receives no traffic. If an exact autonomous two-year deletion schedule is required, a separate scheduled Worker (or an approved external caller) is an unresolved architecture decision. Do not add or enable one silently. [Pages Functions API](https://developers.cloudflare.com/pages/functions/api-reference/), [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

## Required acceptance evidence before production

- Run Functions with local workerd/Miniflare and real local D1/KV bindings; test migrations on an empty database and a representative existing database.
- Test simultaneous duplicate punches, replayed/expired challenges, wrong-store access, locked users, revoked sessions, oversized or malformed JPEGs, failed KV writes/deletes and retry recovery.
- Run a browser flow against those Functions: administrator-created account, branch/GPS and shift assignment, employee login, live capture, Timemark encoding under 200,000 bytes, submission, private photo retrieval and authorized report export.
- Measure deployed free-tier CPU separately before describing runtime compliance as proven. Local successful execution is evidence of API compatibility, not a production CPU-limit guarantee.
- Keep migrations, retention/deletion execution and deployment unapplied until a separately authorized production change. Test deletion semantics only against disposable local data.
