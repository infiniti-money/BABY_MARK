# RC.15 — Attendance recovery
- The browser records only the challenge ID, assignment ID and direction in tab sessionStorage under the authenticated user's ID before submitting. No photo, location, token or password is added to this record. The memory fallback cannot survive a reload when storage is unavailable. Other tabs/devices remain protected by D1 constraints.
- Every failed/invalid submit response is treated as uncertain; no automatic retry. Verify via GET /api/attendance/status. READY allows replay of the same challenge/photo before expiry, not a new capture. If the photo is unavailable after reload, explicitly cancel the unused request.
- POST /api/attendance/cancel atomically changes only an owned READY challenge to FAILED; PROCESSING and COMPLETED are untouched. A delayed submit and cancellation cannot both claim the challenge. No KV cleanup or forced reset.
- Status recognizes an already-recorded attendance for the same user, assignment and direction even if recorded through a different challenge. An orphan COMPLETED record remains UNKNOWN. Failed status checks retain the recovery lock.
- 20/25-second client timeout is not a guarantee the server stopped. Explicit checks are required. A new login to the same account in the same tab can recover; closing the tab, clearing storage, or using another device may lose the local marker. Server uniqueness still applies.
- No new migration; no production data, secret, policy or resource changes. Verify physical devices and actual network faults separately.
