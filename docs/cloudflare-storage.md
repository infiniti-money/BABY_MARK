# Cloudflare D1 + Workers KV — no R2 (migration pilot)
Target: 50 employees, 14 stores, JPEG retention 60 days, 2 photos per employee per day, max 100000 bytes each. At 60 days, 6000 photos ≈ 600 MB payload, excluding storage overhead and other KV data. KV free plan: 1 GB/account, 1000 key writes/day, 100000 key reads/day. 4 photos/day at 100 KB will exceed 1 GB; do not assume all shift patterns fit. Monitor actual account usage, alert at 750 MB, do not silently delete younger evidence or silently reject attendance. If cap approached, arrange a reviewed lower image size or alternate storage. Verify image readability before reducing resolution. No R2 required. Quotas may change. KV may be eventually consistent; retry photo viewing when temporarily unavailable.
## Setup
1. Create D1 database babymark-db and execute cloudflare/d1/0001_initial.sql, then 0002_store_catalog.sql and 0003_internal_auth.sql on new DB only.
2. Create KV namespace babymark-timemark. Pages settings → Bindings: D1 DB, KV TIMEMARKS. Do not create an R2 bucket. Use internal D1 accounts, see docs/internal-auth.md. No Supabase Auth configuration required for this path. Do not expose service keys. Root repo; build output docs. Redeploy. /api/cloudflare/health only checks bindings and schema.
3. Read-only pilot GET /api/cloudflare/photo/<record-id> uses internal bearer token, D1 active profile and scoped access. Returns 410 after 60 days based on server time; no public photo URL.
4. Internal helper cloudflare/lib/timemark-kv.mjs stores already server-stamped JPEG binary (not base64), enforces 100 KB maximum, server time and per-key expiry. This helper is not wired to a public write route. KV TTL applies only to images; D1 attendance metadata remains. Tests: node --test cloudflare/tests/*.test.mjs.
## Before production
Implement trusted server stamp/compression, authenticated write API, D1 transactions/idempotency and failure reconciliation, quota monitoring and exception workflow. KV may not show a newly written image immediately. Test image readability, expiry, cross-branch permissions, mobile devices and legal retention policy; do not export or migrate real employee records without authorization. Current Next.js/Supabase backend stays intact; no production migration or Cloudflare resources have been created by this change.
Official docs: https://developers.cloudflare.com/kv/platform/pricing/ and https://developers.cloudflare.com/kv/api/write-key-value-pairs/
